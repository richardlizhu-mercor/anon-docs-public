§6 · New 16-type taxonomy — detection vs type accuracy re-scored on the current source-of-truth taxonomy · are we labeling the correct type?

New 16-type taxonomy (source of truth, 2026-07-14): Payment Card Number, Card Last4, IP Address, MAC Address are now out of scope (dropped from GT + predictions); Single Name → First Name. Scored 3 ways on the same predictions (re-scored, not re-run): detection (PII-or-not, in-scope), cluster (Identity/Street/Institution correct), fine-type (exact PII type correct).
Type-labeling is where the fine-tune earns its keep. On detection the OOB ai4privacy and our deberta_ft are close (§3 0.815 vs 0.960, §5 0.687 vs 0.607), but on fine-type the gap explodes — deberta_ft 0.959 vs ai4privacy 0.459 on §3 (0.585 vs 0.282 on §5): the OOB detects PII but assigns the wrong type (its ai4privacy label space only loosely maps to ours), while the FT was trained on this taxonomy. Gemini also drops steeply detection→fine (§5 0.664→0.383) — a crosswalk / coarse-label artifact, not a detection miss. deberta_ft has almost no type confusion where it counts (§3 detection 0.960 = fine 0.959).
Retrained on the new taxonomy — two variants. Both fine-tune from the original FT encoder (head reinit 41→33), with PAN/Card4/IP/MAC dropped and Single Name→First Name; §4 is omitted below (it is the train set). (1) slice — the surviving ~1,200-doc §4 slice (the full train_v3 was lost to the /tmp cleanup). (2) full regen — I rebuilt ~5k training docs: val5k's TRUE coordinate-exact GT for the synthetic portion + Gemini distillation for the real-company docs. (A naive Gemini re-label of the synthetic val5k first regressed §3 to 0.699 — Gemini emits only a coarse name category, collapsing the fine name subtypes; using val5k's own GT fixed it — the lesson: use GT where you have it, distill only where you don't.) Result: the full-regen model beats the original on §1 (fine 0.656 vs 0.604) and §5 (0.724 vs 0.585), recovers §3 to 0.829 (slice 0.818, naive-Gemini 0.699) with far better fine-macro, and crushes the OOB on correct-type everywhere. It still trails the original on §3 (0.829 vs 0.959) — that residual is the lost original train_v3 (§3 is in-distribution for the original), which can't be fully reproduced. Bottom line: the full-regen model is the best taxonomy-correct detector — ship it for the new 16-type taxonomy; the original keeps a slim §3 edge only because it stays on the old taxonomy and saw data we've since lost.
GLiGuard through our harness (apples-to-apples). We ran hivetrace/gliner-guard-uniencoder — the anon-playground detector — as a span detector in this harness at its recall-bias threshold 0.40 (same labels as our gliner2). Model-only (no regex pre-pass), it underperforms deberta_ft on every section: detection §1 0.628 / §3 0.731 / §4 0.227 / §5 0.575 (vs deberta_ft higher throughout), and fine-type collapses (§3 0.280, §4 0.086) — the same OOB label-space failure as ai4privacy (detects some PII but mislabels the type, and misses the URL/ID-heavy §4). The playground's reported anobench-v2 ~0.90 is the full pipeline (33-pattern regex pre-pass + recall-bias + their 13-PII/9-PHI labels on anobench), not the encoder — so it isn't comparable to a standalone detector. Takeaway: GLiGuard's value is its pipeline engineering (window-dedup, leak gates), not the model; as a detector, deberta_ft wins.

Verdict

Tokenization: on the fields production scans, the local lane is solved (0.90–0.97). Pick on negative-space precision + cost: deberta_ft ($167/TB) is the value pick and the local-lane anobench leader (behind only Gemini 0.930 and routed 0.910), and it actually beats Gemini on our own synth (§3 0.960 vs 0.796); gliner_know_large wins only where email-metadata negatives reach the detector (§1 all-cols) at ~3× cost; the anobench routed edge does not transfer. The 7B LLM (~$3.9k/TB) and openai_pf are priced/throughput-out. Gemini is the accuracy ceiling but ~$242k+/TB and quota-bound.

IR: the shipped Qwen3-Emb-0.6B + identity LoRA wins across the board — §1 world (AUC 0.864), §2 synth (0.792), and §5 with header context (AUC 0.993 / ARI 0.95); the LoRA beats base Qwen and crushes old-prod MiniLM, with its clearest edge on the production ir-formatted string (§5 ARI 0.504 vs base 0.098). String matching is at chance. Encoder-only clustering needs a linking signal — co-occurrence (§3 multi-service) or the email header (§5); bare disjoint surfaces collapse, so the benchmark's mention construction matters as much as the encoder.

Caveats

  • Price/speed/compute are the §2 compute-model figures (GFLOPs → H100 MFU 35%); measured local docs/s (this Mac) confirm the ordering. Combos costed as their component sum; presidio is CPU.
  • Gemini re-run live (Vertex, gemini-2.5-flash) on §1/§3/§4/§5; the §2 column uses the reviewed chart's 0.919. §4's Gemini is circular (its GT = Gemini's labels).
  • §4 is in-distribution for the fine-tuned models (their train set) — flagged.
  • §1/§5 IR clustering uses a best-threshold (oracle) ceiling; AUC is the threshold-free headline. §5's 2-surface identities read as degenerate under body-only context; giving the mention builder the observed From-header block (name↔email) makes it a usable — if narrow — bench (shipped qwen-lora AUC 0.993 / ARI 0.95). The shipped LoRA is loaded via explicit PEFT (a SentenceTransformer(adapter_dir) auto-load silently mis-maps the adapter under sentence-transformers 5.x).
  • §5 env decay: deberta_ft / deberta_ai4privacy / gliner2_ft / routed / piiranha are N/A on §5 — their /tmp scratch checkpoints/scripts were purged by the macOS /tmp cleaner (~3 days) and can't be faithfully reproduced (no config/train data). All other options ran; env rebuilt in a fresh venv.
  • sisyphus is the deterministic LLM-free anonymizer (schema always-PII columns + regex email/url/phone + aho-corasick name-sweep of collected values), run via its real Rust binary and scored by diffing original vs anonymized cells. It's precision-perfect but recall-limited (no NER): §5 content 0.790 (R 0.65, names+emails in structured cols), §1 content 0.485 (R 0.32, rich inline types it can't reach). N/A on §2 / §3 / §4 — it needs a schema'd extraction table: §2 is a masked tree, §4 is free-text docs, and §3's eval corpus is preprocessed (join/clean) so spans don't align to sisyphus's raw-cell diff (a from-raw §3 run is deferred). Fastest + cheapest by far (11k docs/s CPU, no GPU/LLM).
