Data Acquisition · Anonymization · Identity Resolution

Identity Resolution: from a single Leiden pass to a learned pairwise engine

Stage 2 of the anonymization pipeline used to be one big activity that scored values by cosine similarity and cut the whole graph with a hand-tuned Leiden pass. We rebuilt it. The new engine (feat/ir-eag-free-engine) runs a per-type Temporal fan-out around a Qwen LoRA encoder, a 259-feature LightGBM pairwise scorer, and per-component Leiden at a resolution the model learns instead of one we guess.

Status: Draft apps/server/data-acq branch: feat/ir-eag-free-engine Stage 2 · Identity Resolution Updated 2026-07-06
The short version Today's prod engine is one ~2,500-line Temporal activity. It embeds values with MiniLM, scores candidate edges with a hand-tuned weighted-signal combiner, and runs one global Leiden per type at resolutions we picked by hand. The rebuild keeps that goal but moves the decision into a model. A LightGBM classifier now scores each candidate pair over a 259-feature bank, fed by per-type Qwen LoRA embeddings from a Modal GPU and by FAISS/co-occurrence/token blocking, and returns a calibrated P(merge). We keep the edges above a learned per-type τ, break them into connected components, and run Leiden per component at a learned γ, with hard CANNOT-LINK and MUST-LINK rules on top. On synthetic benchmarks the new engine gets better as data scales (F1 0.68→0.84 from 2K to 13K) while today's engine gets worse (0.75→0.71), and it merges far more precisely (P≈0.96 vs 0.75). 1 · Where Identity Resolution sits

The anonymization pipeline takes raw SaaS data (GitHub, Slack, Linear, QuickBooks, and so on) and produces a realistic synthetic copy. Every piece of PII or BII gets swapped for a fake, but the shape of the data survives: referential integrity, formats, and structure all stay intact. There are four stages, and IR is the second.

Why IR matters

Detection hands us thousands of raw values, and a lot of them are the same person wearing different clothes: John Doe, jdoe@company.com, j.doe, jsd_77. Fake each one independently and John turns into four strangers, so the data stops hanging together. IR groups those values into one identity, and that identity gets a single fake everywhere it shows up.

Why we lean toward precision The two failure modes aren't equal. Merge two different people and they share a fake identity, which is a privacy leak, and it corrupts two workflows rather than two rows. Split one person into two fakes and you've got a cosmetic problem. So the engine stays conservative about merging. That bias is also why the clustering step, not the pairwise scorer, is where things get hard.

2 · Today's production engine — origin/main

One activity: cosine similarity fused into a graph, then a single global Leiden cut. This is the engine the rebuild replaces.

On origin/main, IR is a single ~2,526-line Temporal activity behind one IdentityResolutionWorkflow. It classifies every value with an LLM, embeds them on the CPU worker, scores candidate edges with a hand-tuned combiner of five similarity signals, and then partitions the resulting graph with one global Leiden run per cluster type. Where it strains

What it gets right

  • It's type-aware, so each PII type gets similarity rules that suit it.
  • Leiden's modularity objective shrugs off some noisy edges. That's why it replaced connected-components in the first place.
  • The resolution knob is interpretable, and the over-merge guards give hard privacy floors.

Where it hurts

  • The scorer doesn't learn anything. It's a fixed weighted sum, so it can't figure out that two same-attribute look-alikes with high cosine are usually different people.
  • Almost everything is tuned by hand (five weights, per-type thresholds, per-type resolutions) on roughly one company's data. Precision actually drops as the corpus grows.
  • The global auto-tuner raises resolution to break up one runaway cluster and shatters good clusters elsewhere as a side effect.
  • MiniLM is a generic embedder, not tuned for PII strings, and it runs on the CPU worker.
  • It's one opaque box. Any failure re-runs the whole thing, and the 201 MB clusters.json is a single-cell serialization we regret.

3 · The rebuild — feat/ir-eag-free-engine

A learned pairwise merge decision, wrapped in a per-type Temporal fan-out.

This is a ground-up rewrite: 149 files, +20,459 / −11,733 in the IR module, 68 commits. What actually changed is what makes the merge decision. Instead of folding signals into edge weights and letting a global algorithm carve the graph, the engine now asks a trained model a direct, symmetric question for every candidate pair, "are these the same entity?", and only clusters once it has those answers.

Leiden isn't gone, it's demoted "Leiden = old, learned-pairwise = new" is a handy shorthand, but the truth is a bit narrower. What's gone is the global, hand-tuned Leiden. Leiden itself survives, now running per component at a learned resolution γ, downstream of the pairwise scorer over edges the GBDT already thresholded. It's one step in the clustering tail rather than the thing that makes the call. (An earlier round of experiments tried average-linkage agglomerative clustering with a fine-tuned bge encoder; the version that shipped uses Qwen LoRA plus per-component Leiden.)

The S0–S8 stage kernel

We broke the monolith into a typed stage kernel, and each cluster type runs through it on its own. There's no S2 file: encode moved out to the GPU service, so the stages read S0 through S8 but only eight of them actually exist.

The encoder — Qwen LoRA on a Modal GPU

The old in-process MiniLM (384-d) is out. In its place is a shared Qwen/Qwen3-Embedding-0.6B base with 5 frozen per-type LoRA adapters (Identity, Org, Brand, Product, Street) producing L2-normalized 1024-d fp16 vectors, served on a warm Modal GPU (a10g). Each value is formatted as "{cluster_type} {attribute_type}: {preprocessed_value}". There's deliberately no CPU/bge fallback: if the encoder is down, the run stops rather than quietly embedding with a different model than the one the adapters were trained on.

Why bother with the GPU rebuild MiniLM is a generic sentence embedder that was never tuned for alias matching. The per-type Qwen LoRA path measured recall@50 of 0.9487 against bge's 0.8003 in the lab, and it moves the dominant encode cost (roughly 87% of encode+FAISS at Identity's ~197K nodes) off the CPU worker onto a GPU. FAISS became dim-agnostic along the way, reading shape[1], so the 1024-d array works without a hardcoded-dim crash.

Candidate blocking — three arms, three columns

Scoring all O(n²) pairs is a non-starter, so blocking (S3) cuts it down to candidates using three arms, unioned in one global index space and kept as three separate columns (we never max-merge them, because the GBDT wants to read them apart):

  • FAISS kNN, k=200, streamed in 4,096-row batches (that's the "444 MB streamed" invariant), IVF index above 5,000 nodes. Top-30 neighbour cosines get harvested inline so the embedding features don't need a second index scan.
  • Co-occurrence: any pair sharing a (service, table, row) record becomes a candidate, even when the strings look nothing alike.
  • Token / cross-attribute: Identity token blocks plus name↔abbreviation pairs for 7 types, with caps on hot tokens and fan-out.

The 259-feature GBDT pairwise scorer

This is where the decision lives. A LightGBM model reads a 259-column feature vector per candidate pair and returns a calibrated P(merge). Every feature is symmetric in the two values, which is what keeps the decision order-invariant. The old 19 production features are still in there, re-homed byte-for-byte into their families. One vectorized compute_features() runs at both training and serving time, so there's no train/serve skew to chase.

Why a raw Booster with a separate calibrator instead of a scikit wrapper? The base fit has to stream over parquet blocks, because the pooled (N, 259) matrix won't fit in memory at Identity scale, and keeping the tiny 1-D sklearn calibrator apart from the LightGBM C-model shrinks the pickle surface. The loader stamps and checks four library versions on load so a cross-version pickle can't mis-load silently.

Learned calibration — per-type τ and γ

This was the deepest change, and the source of the nastiest bugs. The old constants were tuned to a dead cosine distribution, which makes them meaningless on a calibrated GBDT probability. The new engine re-derives its operating point directly on the calibrated P-scale, using a "train-through-serving" harness that runs synthetic fixtures through the exact same serving code prod uses:

  • τ, the merge threshold. A starvation-aware selector: hold the 0.95-precision floor unless it can only be met at recall below 0.10, in which case fall back to F1-max. The same rule lands Identity at τ≈0.55 (its chaining would otherwise flood Leiden) and pushes low-signal attribute types to F1-max, with nothing tuned by hand.
  • γ, the Leiden resolution. A label-driven crossover: γ sits between the 90th percentile of negative weights and the 10th percentile of positive ones, capped just under the positive floor so it can't degenerate.
The bug this fixed: "measured but never served" For weeks, training stamped τ and γ into the bundle and serving ignored them. It cut every type at a flat config τ and ran Leiden at empty hand-tuned resolutions, so the calibrated operating point was measured but never actually used. merge_threshold() was dead code. Two calibrator bugs were hiding behind that: a degenerate γ=1.0 that produced zero clusters, and a starving τ=0.98 that produced zero edges. Together they were the merge-blocker; fixing all three took offline F1 from 0.000 to 0.734. There's no default τ/γ table anymore. Resolution goes operator-override → bundle → fail-loud for τ, or singleton for γ.

The clustering tail — WCC → per-component Leiden → constraints

Edges above τ get broken into weakly-connected components. A P≥τ edge can't cross a component, so this split loses nothing, and each component clusters on its own:

  • Per-component Leiden/CPM at the learned γ, fixed 10 iterations, seed 42, byte-deterministic. A component over 50K edges fails loud with HubLeakError rather than silently degrading.
  • CANNOT-LINK runs as a pure final split. Five predicates (org-suffix-only overlap, street house-number, first-name homonyms, email-domain-vs-org, cross-role-same-container) apply after Leiden, so the constrained result is always a subset of the unconstrained one.
  • MUST-LINK is exact-normalized equality plus ghost "certain" pins for extend mode. Co-occurrence is never a MUST-LINK; it's soft evidence, and the GBDT plus CANNOT-LINK make the actual call.

Components only materialize the ~2.8% of nodes that carry a surviving edge. The ~97% edge-isolated majority gets refilled as singletons at S8, so every value still reaches the faker.

Co-occurrence & the Enterprise Activity Graph

Co-occurrence is the evidence the encoder can't see. Two people named "J. Smith" look identical but never share a row; a person's name and their email look nothing alike but sit in the same (service, table, row). The new engine rebuilds co-occurrence from the deduped nodes' service-qualified source_records self-join. The old stored array turned out to overlap the true shared-row topology by under 2%. A structural role gate drops cross-person edges at the source, so a sender and a recipient in one email row don't get linked. Co-occurrence then shows up in three places: a candidate arm, a Leiden edge weight, and about 43 of the 259 features (the cooc and graph families).

Two different things are both abbreviated "EAG"
  • Enterprise Activity Graph (design doc v0.1) is the north-star: a persistent typed graph (G_obs → resolved → G_anon) of cross-service activity. IR is "Stage 1" of it, and its role for IR is explicitly "drop-in features, not a replacement". It hands IR pair features (co-occurrence, rare_context_overlap, structural anchor edges) through an "EAG Features for IR Consumption" contract. That's the sense in which the GBDT reads "features from the EAG."
  • Embedding-Anchor-Graph is the old live-LLM-judge path built on a G_obs neighborhood. The branch is called eag-free because it deletes that dependency. The shipped engine builds its own activity-graph signal straight from the masked data's (service,table,row) self-join, with no separately-built graph and no live LLM judge.
So the engine today captures the activity-graph idea as the cooc and graph feature families over structured data. The fuller typed EAG, with AUTHORED_BY/SENT_TO/ IN_CONTEXT edges and cross-modal documents, is future work (DACQ-2809).

Temporal fan-out orchestration

The whole thing runs as IRFanoutWorkflow. It routes once, then fans out one durable unit per cluster type (the full encode→block→score→reduce→wcc→cluster chain) across a sliding window of 4 on a dedicated worker/queue at 64 concurrency, largest type first so Identity (~77% of encode work) starts early. It continue-as-news when history pressure builds, then builds once at the end. Every activity boundary carries only S3 keys and scalars, never an ndarray or an edge blob, so workflow history stays flat no matter how much data moves. Encode is a durable start→poll→cancel triad, because Modal spawns aren't idempotent.

4 · Why the framing is "pairwise & order-invariant"

The real change is the unit of decision. The old engine decided globally: it partitioned the whole graph at once, and any two nodes' fate hung on the entire edge structure around them. The new engine decides locally, one symmetric pair at a time, then composes those decisions with lossless components and per-component Leiden.

Deciding per symmetric pair gets us three things that matter for a privacy-critical, auditable pipeline. It's deterministic: fixed seeds and single-threaded kernels mean the same input always yields the same clusters. It's auditable, since every merge traces back to one pair, one 259-vector, one probability. And it's learnable, because a symmetric pair is a clean supervised example, so the rule gets trained and calibrated instead of hand-tuned.

6 · What we learned (offline benchmarks)

Both engines are scored by the same metric code. A dual-path reader normalizes clusters.json and clusters.parquet to one schema, so the F1 gap is a pipeline gap, not a metric gap. Two synthetic fixtures, and the numbers are directional rather than production SLAs.

The trend flip HEAD F1 climbs with scale (0.68→0.84) while main slides (0.75→0.71), and HEAD is far more precise at both sizes (0.96–0.97 against 0.75–0.86, so fewer wrong merges). At 2K, HEAD's recall is the binding constraint; it just emits fewer merges. At 13K, more data per identity lets the learned scorer, the calibrated τ/γ, and CANNOT-LINK find genuine merges while precision holds. That's the opposite of the global cosine engine, whose precision decays as more surface forms create accidental over-merges. Shipped bundle pm_qwen_gbdt_v2, 259 features, CV F1max 0.9332.

The lesson that stuck: run it, don't just read it

Eight bugs only turned up when we ran the pipeline end-to-end. Static review caught none of them. Three of the eight formed a single merge-blocker that produced zero clusters until we fixed all three:

Orphaned calibration

Training stamped τ/γ; serving never read them, so Leiden ran empty hand-tuned constants.

Degenerate γ = 1.0

γ set to P90-of-positives piled up at ≈1.0, so CPM merged nothing and produced 0 clusters.

Starving τ = 0.98

A precision-floor τ dominated for low-signal types, pinning recall near 0.

The other five: an eval child-workflow self-collision, an eval parquet-read crash, a 0-candidate crash, an uncalibrated-type fail-loud gap, and an over-strict faker cross-identity collision guard (the "heer" crash).

7 · Where this is going

Cross-modal IR (DACQ-2809)

Resolve structured columns and free-text documents in one IR run. The source_records triple is already modality-agnostic (source, container, co-mention group), so adding a modality is a caller-side list append, not a contract migration.

The fuller Enterprise Activity Graph

Promote the pragmatic co-occurrence signal to the typed G_obs with AUTHORED_BY/SENT_TO/IN_CONTEXT edges, and feed rare_context_overlap in as another pair feature. Drop-in features, not a replacement.

GBDT → MLP as data grows

LightGBM is the right tool while labels are scarce. As labeled merge pairs pile up, an MLP over the same (or a richer) feature space should scale better with data and could eventually share the encoder representation for a more end-to-end decision. The scorer is a clean duck-typed interface, so swapping the model stays contained.

Real-data validation

The head-to-head numbers are on synthetic fixtures, and ship validation is still a manual First-Quadrant diff. More real, labeled data is what lets the learned operating point default-on more widely.

Glossary

  • Enterprise Activity Graph (EAG) — north-star typed activity graph (G_obs → resolved → G_anon); IR is its Stage 1; supplies drop-in pair features.
  • Embedding-Anchor-Graph (EAG) — the old live-LLM-judge path the eag-free branch deletes. Same acronym, different thing.
  • Order-invariant — P(merge | a, b) = P(merge | b, a); every feature is symmetric.
  • τ / γ — the learned per-type merge threshold (on calibrated P) and Leiden CPM resolution.
  • WCC — weakly-connected components; the lossless shard primitive that lets Leiden run per-component.
  • train-through-serving — training runs fixtures through the same serving code prod uses, so there's no train/serve skew.
